Windows 11 Wi‑Fi 故障排查与修复记录

问题：Wi‑Fi 消失 / WLAN AutoConfig 启动失败（Error 1068），之后进一步发现 IPv4/DHCP 问题。

最终结果：Wi‑Fi 服务已经恢复，可以连接网络并正常上网。
主要修复：发现 Wcmsvc 因依赖 WinHttpAutoProxySvc 启动失败而无法启动；最终将 Wcmsvc 依赖调整为 RpcSs/NSI，之后 Wcmsvc 与 WlanSvc 可以启动。

一、故障链总览

WlanSvc（WLAN AutoConfig）
        │
        ├── nativewifip   → Running
        ├── RpcSs         → Running
        ├── Ndisuio       → Running
        └── Wcmsvc        → 原本无法启动
                           │
                           ├── RpcSs                  → Running
                           ├── NSI                    → Running
                           └── WinHttpAutoProxySvc    → 启动失败 10022
最终关键点： WinHttpAutoProxySvc 启动时报 Service-specific error 10022， 导致 Wcmsvc 报 1068，进一步导致 WlanSvc 报 1068。

二、项目 1：检查 WLAN AutoConfig（WlanSvc）

1. 查看 WlanSvc 配置

sc.exe qc Wlansvc

作用：查看 WLAN AutoConfig 的启动方式、程序路径和依赖服务。

项目结果 / 含义
START_TYPEAUTO_START：Windows 自动启动
DISPLAY_NAMEWLAN AutoConfig
依赖nativewifip、RpcSs、Ndisuio、wcmsvc

2. 尝试启动 WlanSvc

net start WlanSvc

结果：System error 1068。

含义：WlanSvc 自己不是最底层故障，而是它依赖的服务/组件没有启动。

三、项目 2：逐个检查 WlanSvc 依赖

nativewifip

sc.exe query nativewifip

最终确认：RUNNING。

注意：之前曾经输入过 nativewifiip，这是多了一个 i 的错误拼写。 正确名称是 nativewifip。

RpcSs

sc.exe query RpcSs

结果：RUNNING。Windows RPC 基础服务正常。

Ndisuio

sc.exe query Ndisuio

结果：RUNNING。WLAN 相关网络 I/O 组件正常。

Wcmsvc

sc.exe query wcmsvc

结果：STOPPED，并且启动时报 1068。

四、项目 3：检查 Wcmsvc 的真正依赖

查看配置

sc.exe qc wcmsvc

实际看到的依赖为：

DEPENDENCIES
    RpcSs
    NSI
    WinHttpAutoProxySvc

检查 NSI

sc.exe query nsi

结果：RUNNING，因此 NSI 不是故障点。

检查 WinHttpAutoProxySvc

sc.exe query WinHttpAutoProxySvc

结果：

STATE              : 1  STOPPED
WIN32_EXIT_CODE    : 1066
SERVICE_EXIT_CODE  : 10022

于是直接测试：

net start WinHttpAutoProxySvc

结果：

The WinHTTP Web Proxy Auto-Discovery Service service is starting.
The WinHTTP Web Proxy Auto-Discovery Service service could not be started.

A service specific error occurred: 10022.
真正的底层故障：
WinHttpAutoProxySvc 无法启动，具体服务错误码为 10022。

五、项目 4：系统文件完整性检查

SFC

sfc /scannow

结果：Windows Resource Protection 没有发现完整性违规。

含义：没有发现普通系统文件损坏，因此没有继续通过 SFC 修复。

DISM

DISM /Online /Cleanup-Image /RestoreHealth

执行过程中曾长时间停在约 64.4%。CBS 日志仍有活动，但最终手动取消，返回：

Error: 1223
Operation was incomplete because of a cancel request.

所以 DISM 不是一次成功完成的修复，不能把它当作已修复项目。

六、项目 5：确认 Wi‑Fi 驱动文件

dir C:\Windows\System32\drivers\nwifi.sys

结果：nwifi.sys 文件存在，大小约 991232 bytes。

意义：至少说明相关 Native Wi‑Fi 驱动文件并没有简单地“完全不存在”。

七、项目 6：修复 Wcmsvc 的依赖关系

为了绕过无法启动的 WinHttpAutoProxySvc，修改 Wcmsvc 的依赖：

sc.exe config Wcmsvc depend= RpcSs/NSI

结果：

[SC] ChangeServiceConfig SUCCESS

即把 Wcmsvc 的依赖从：

RpcSs
NSI
WinHttpAutoProxySvc

调整成：

RpcSs
NSI

然后启动 Wcmsvc

net start Wcmsvc

启动成功。

再启动 WlanSvc

net start WlanSvc

启动成功，Wi‑Fi 功能恢复。

重要：这一步是“绕过” WinHttpAutoProxySvc 的故障，不等于 WinHttpAutoProxySvc 本身已经修好。

八、项目 7：Wi‑Fi 能连接，但显示“无 Internet”

检查 IP

ipconfig

Wi‑Fi 当时得到：

Autoconfiguration IPv4 Address : 169.254.190.129
Subnet Mask                    : 255.255.0.0
Default Gateway                : 没有 IPv4 网关

169.254.x.x 是 APIPA 地址，通常表示 Windows 没有从 DHCP 服务器拿到正常 IPv4 地址。

尝试重新获取 DHCP 地址

ipconfig /release
ipconfig /renew

当时 /renew 显示 Wi‑Fi：

An error occurred while renewing interface Wi-Fi:
An invalid argument was supplied.

此时 IPv4 仍然是 169.254.x.x。

九、项目 8：网络协议栈修复（当时准备执行）

曾准备使用：

netsh int ip reset
netsh winsock reset

但是后来用户反馈已经重新连上并可以正常上网，因此不需要继续执行这些命令，也没有必要重启。

最终状态：无需进一步网络重置，网络已经恢复正常。

十一、当前已知的“未完全修复项”

  1. WinHttpAutoProxySvc：仍然存在 10022 启动错误。当前只是从 Wcmsvc 的依赖链中移除了它。
  2. DISM：没有成功完整执行 RestoreHealth，因此不能说 DISM 修复完成。
  3. Wcmsvc 依赖：已经被修改。如果以后使用企业代理、WPAD、某些 VPN 或特殊网络环境出现问题，需要重新检查这一项。

十二、以后如果 Wi‑Fi 又坏了，建议先检查这 5 项

sc.exe query WlanSvc
sc.exe query Wcmsvc
sc.exe query RpcSs
sc.exe query nsi
sc.exe query WinHttpAutoProxySvc

如果普通 Wi‑Fi 已经可以正常上网，不要为了“看起来更干净”而重新修改这些服务。

最终结论： 本次故障主要经历了两层：
① WLAN AutoConfig 1068 → 找到 Wcmsvc 依赖链 → WinHttpAutoProxySvc 10022 → 调整 Wcmsvc 依赖后恢复 WLAN。
② Wi‑Fi 恢复后 IPv4 一度拿到 169.254.x.x → DHCP/IPv4 层异常 → 随后网络自行恢复，最终可以正常联网。
